# QNotch for macOS

Status: functional development milestone, not a public release. A native Swift/AppKit menu-bar app provides a display-anchored notch surface with a hover panel and the feature modules listed below. Which Windows features exist on the Mac, and how, is tracked in the [parity table](parity.md). The notch surface shares the Windows visual language (near-black surface, bordered cards, icon tab strip, soft-accent chips) built from AppKit: SF Symbols, system typography, the macOS accent color, native focus, accessibility, and Core Animation. Settings is a System Settings–style sidebar window that follows the system appearance. Windows remains independently released.

## Requirements and commands

- Apple silicon (arm64), macOS 13 or newer. Intel and universal downloads are not supported by this milestone.
- Xcode 15 or newer, including its macOS SDK and XCTest; Swift 5.9 or newer. One package dependency, [Sparkle](https://sparkle-project.org) for updates, pinned exactly in `Package.swift` and `Package.resolved`; SwiftPM fetches it on the first build. No Windows tooling.
- A logged-in graphical macOS session for the native UI smoke test and interactive app. Headless geometry/state/settings tests run through XCTest.
- The deployment target is macOS 13. CI runs on macOS 14; development evidence also records the local OS. Compatibility on a physical macOS 13 machine still needs validation before a public release.

From the repository root:

```sh
bash scripts/macos/build.sh
bash scripts/macos/test.sh
bash scripts/macos/smoke.sh
open dist/macos/QNotch.app
```

Builds produce `dist/macos/QNotch.app` with release optimization and warnings treated as errors. No signing account, certificate, provisioning profile, or network service is needed. The development app bundle has no Developer ID signature or notarization. The toolchain may emit a local ad hoc executable signature; that is not distribution signing. Do not distribute this build as a public download.

If Command Line Tools are selected, the build/test scripts use `/Applications/Xcode.app` when available, for that process only. For a different Xcode installation, set `DEVELOPER_DIR` to its `Contents/Developer` directory. They report a missing full Xcode installation explicitly. They never change the machine-wide developer directory. Use `xcrun swift --version` to inspect an explicitly selected toolchain.

For an isolated interactive session:

```sh
QNOTCH_MAC_DATA_DIR="$(mktemp -d)" open -n dist/macos/QNotch.app
```

Alternatively, launch the executable with `--data-dir /absolute/temporary/directory`. Each data directory has its own advisory instance lock. Quit only the test instance you started, using its menu or PID. A second instance with the same directory exits instead of silently overwriting settings.

## Behavior and availability

- Choose the main display or a specific connected display in Settings. If the selected display disconnects, QNotch falls back to the main display and reports the unavailable selection; reconnecting restores it. With no display, the panel is hidden.
- Placement uses `NSScreen.safeAreaInsets` and its auxiliary top areas. On a notched display, the black surface joins the top bezel and wraps the physical camera housing. The occluded center is reserved: the app icon and status segments live in the clear side wings, while panel controls start below the housing. The panel uses the status-window level so the menu bar cannot hide the wings. If macOS cannot report valid housing geometry, it explicitly falls back to a pill below the safe boundary. Displays without a notch use a pill six points below the menu-bar working area. Coordinates are points, including negative display origins; no model-name or fixed notch-width heuristics.
- Idle, the surface exactly covers the camera housing. Status (a running or paused timer) grows symmetric wings beside it; the panel springs out of the notch on open (about 3% overshoot) and settles quickly on close. Shape morphs are Core Animation path animations rendered by the compositor; during a morph the window briefly covers both shapes plus overshoot room, then returns to the exact surface. Tab changes slide the indicator and content; buttons and chips have hover and press feedback.
- Hover opens after 120 ms and collapses 400 ms after leaving (Settings, General: 0–600 ms and 100–1500 ms). **Keep panel open** (the pin in the header, or Settings, General) stops pointer leave, outside clicks and focus loss from closing it; Escape, the pin and the toggle hotkey still close it, and a pinned panel opens at launch. Hover never activates the app or accepts keyboard input. After an explicit close (Escape, Settings, Show, Pick a color, launching an app) with the pointer still on the notch, hover does not reopen the panel until the pointer has left it; Show and app launches leave the keyboard with the app they bring forward. Clicking the pill/panel or choosing **Open Panel** explicitly grants keyboard focus. A keyboard-opened panel stays open on pointer leave; Escape, outside click, or key-window loss closes it. Closing never forces focus back after the user has already switched apps.
- Home shows the cards of the enabled features in a three-column grid (cards are one or two columns wide), and scrolls when they overflow. The panel body is 700 × 376 points.
- Welcome tour ([spec](../../spec/onboarding.md)): on a fresh install (no `general.json`) a dark, Raycast-style window opens before any module is constructed, so the feature choices apply directly. Steps: `welcome` (the notch with live-looking segments and the panel opening below it), `open` (the toggle shortcut as key caps, **Change** with the Settings, Hotkeys recorder and its conflict messages, and *Try it now*: the gesture is noticed in the tour window while the global hotkeys pause, so no hook is added), `features` (a tile and switch per feature in the spec's three groups, with **Turn all off/on**), `connect` (rows the GitHub, Weather and Agents modules provide through a static `setup` factory in `ModuleInfo`; left out when none of them is on or has a row) and `finish` (**Check for updates automatically**, **Open at login**, tips with the real Search shortcut, the menu-bar item and file drops, and **Open QNotch**, which opens Home with the keyboard). Return continues, Esc and the close control skip, Back and progress dots sit in the footer, and every control has an accessible name. Motion follows the spec's Motion section with Core Animation (`Shell/MotionKit.swift`): the window rises in; steps slide by direction with a parallax hero and staggered text; each step has a one-time hero moment (the notch dropping in and the panel unfolding, the cursor gliding to the notch and the key caps pressing, tiles staggering and dimming when off, the GitHub grid's diagonal wave, the "QNotch is ready" check drawing); success moments use a spring; and **Open QNotch** flies a picture of the tour into the notch in a click-through overlay while the panel springs open. Only opacity and transforms animate, toward model values that are already final. The two loops (the glow drift, the key caps) and the sign-in's waiting dot run only while their step is shown and the window is visible (`occlusionState`), and are removed otherwise. Reduced motion (the system setting or QNotch's own) leaves 120 ms crossfades; `--smoke-test` cuts every animation, so its snapshots show the settled state. Skipping keeps what was already chosen; on a first run it also turns on automatic update checks and leaves login items alone. A run with an isolated data folder starts with **Open at login** off. Settings from before the tour are marked `onboardingDone` silently; an unreadable `general.json` is never rewritten; a tour that never ended (quit midway) shows again. Settings, About, **Show Welcome Tour** opens it any time; there, as in Settings, the switches apply at once (also the feature switches, since Mac features start and stop without a restart). `--smoke-test` and `--measure` never show it automatically.
- Settings, Features has one switch per module. A module that is off is never constructed: no timers, listeners, hotkeys, cards, tabs, segments, sounds or settings page. Changes apply immediately, without a restart.
- Global hotkeys use Carbon `RegisterEventHotKey`, which needs no Accessibility or Input Monitoring permission. ⌃⌥N toggles the panel with keyboard focus; ⌃⌥F opens Search with the cursor in the box (pressed again there, it closes the panel). Settings, Hotkeys records new gestures (a gesture needs ⌃, ⌥ or ⌘; Esc cancels; Delete turns it off) and reports a key another app already owns or another QNotch shortcut already uses.
- Settings, Sounds lists every sound the enabled features can play. Each plays a macOS system sound (from `/System/Library/Sounds` and `~/Library/Sounds`) or an audio file the user picks, falling back to the default if the file is missing. Whether a sound plays at all is set on its feature's page.
- The panel header shows the user's first name, the date, the Home / Search / module tabs, and Settings. Home hosts the cards of enabled features; features add their own tabs. Search is a tab: with keyboard control, typing anywhere (or ⌘F) jumps to it, and Return runs the first result. Search asks every enabled feature's in-memory search source, then tabs and Settings pages, About included (5 hits per source, in source order). Buttons, tabs, chips, the search field, switches, and pop-ups have accessibility labels. The menu-bar item and the global hotkeys provide keyboard access without an event tap or Accessibility permission.
- Presets are 5, 15, 25, and 50 minutes. Start, pause/resume, and reset work locally; scrolling over the Home card changes the length while stopped. A running timer continues across sleep and refreshes on wake. It stops on quit; only preferences persist. On completion it plays the chosen sound, opens the panel on Home for five seconds without taking the keyboard (Settings, Timer can turn this off; then Done stays in the notch until the panel is next opened), and lines up the next block as on Windows: 25 or 50 minutes are followed by a 5 minute break, a break by 25 minutes. No notification permission is requested.
- Volume shows the default output's level and name on a Home card: a mute button, the percentage (or Muted), and a slider; scrolling over the card changes it by 2%, and raising it while muted unmutes. CoreAudio property listeners report volume, mute and default-device changes, so the card follows the keyboard volume keys and output switches without polling. An output without software volume (some HDMI and USB devices) says so instead of showing a fake slider.
- Note is a plain-text card on Home. Click it to type (clicking gives the panel the keyboard; Escape still closes). The footer shows the last saved date, the word count, and Saved / Editing / Not saved. `note.txt` is read off the main thread at startup (typing before it loads wins), written atomically on a utility queue 500 ms after the last keystroke, and flushed when the panel closes or QNotch quits. Search lists each matching line. Up to 100,000 characters.
- Color picker: **Pick a color** closes the panel and shows the macOS color sampler loupe (`NSColorSampler`; no Screen Recording permission). Click to pick, Esc to cancel. The color is converted to sRGB and copied as `#RRGGBB`; the last six picks appear as swatches that copy again. Nothing runs until a pick starts.
- Mic and camera shows an orange microphone and/or green camera glyph in the right wing while any app uses them; its tooltip and VoiceOver label read "Microphone: Zoom. Camera in use." It only listens: CoreAudio `DeviceIsRunningSomewhere` on every input device, CoreMediaIO `DeviceIsRunningSomewhere` on every camera, and, on macOS 14.2 or newer, CoreAudio process objects (`IsRunningInput`) to name microphone apps. Those per-process listeners exist only while the microphone is in use. Per-app camera use has no public macOS API, so it reads "Camera in use". No permission is requested and nothing is recorded; macOS's own orange and green indicators remain the system's authority.
- System stats: a System card on Home (CPU and memory bars, GPU utilization, network ↓/↑), and stats beside the notch chosen in Settings, System stats: CPU (left) and memory (right) by default; GPU, network, battery and clock are optional because the menu bar already shows battery and time. CPU comes from `host_processor_info` tick deltas, memory from `host_statistics64` (Activity Monitor's Memory Used), network from `getifaddrs` counters of physical interfaces (no loopback, VPN tunnels or AWDL), GPU from IOKit `IOAccelerator` performance statistics, and battery from IOKit power-source notifications. The card samples every second while Home is visible. Collapsed, sampling runs every 5 seconds only while a sampled stat is in the wings; otherwise nothing is sampled. The clock wakes once per minute only while shown. GPU temperature is not available: macOS has no public sensor API.
- Settings, Appearance: the accent color (Automatic follows the macOS accent, or one of the eight Windows swatches), Reduce motion, the header's display name and profile picture (QNotch keeps a 96-pixel square copy as `profile.png`), and a switch per Home card. The notch is always dark, like the bezel; the Settings window follows the macOS appearance. The Windows System/Dark/Light theme is intentionally not ported.
- Settings, General, **Open at login** uses `SMAppService.mainApp`. macOS lists QNotch in System Settings, General, Login Items, may ask for approval there, and shows its own notice when it is added.
- File tray: drag files onto the notch (the panel opens on the Files tab, where a drop target replaces the empty state below the header) or use **Add**. The tray keeps references, never copies, and never modifies or deletes the files; items are saved as file bookmarks in `filetray.json`, so they follow renames and moves, with the path as fallback. At most 60, newest first. The Home card shows the count (and missing files) and the four newest; the Files tab shows Quick Look thumbnails. Click selects, double-click opens, space previews with Quick Look, and dragging a file out offers only copy or link. The context menu has Open, Quick Look, Show in Finder, Share… (the system picker, including AirDrop), Export to Folder… (always copies; names never overwrite), Copy Path and Remove. Thumbnails are generated only while the panel is open and dropped when it closes; nothing runs while collapsed.
- Clipboard history keeps the last 40 text, link, code and image entries in memory (pinned entries on top and never evicted; at most 8 MB of images; text up to 200,000 characters), classified like Windows. A Home card shows the last three; the Clipboard tab filters All/Text/Code/Images, and clicking an entry copies it again. Search finds text entries. macOS has no clipboard change notification, so QNotch compares the pasteboard's change count once a second and reads the contents only after a change. Content that password managers mark with the nspasteboard.org concealed/transient/auto-generated types, Finder file copies, and QNotch's own writes are never captured. **Keep history between sessions** (off by default) saves text entries and pins to `clipboard.json`; images are never saved, and turning it off deletes the file. On macOS 15.4 and later the system may ask once whether QNotch may read the clipboard; if access is set to deny in System Settings, Privacy & Security, Paste from Other Apps, the module stops checking and says so.
- Notifications lets apps and scripts post to the notch, with the Windows request format: `QNotch.app/Contents/MacOS/QNotch notify "Title" "Body" [--level …] [--url …] [--focus] [--action id=Label] [--wait] …` (run `--help`; exit codes 0 sent/answered, 1 dismissed, 2 timed out, 3 not running, 4 error), a Unix socket `notify.sock` in the data folder (mode 0600; one JSON line in, one out), or HTTP on 127.0.0.1 only (`POST /notify`, `?wait=1`, `DELETE /notify/{id}`; bearer token kept in the Keychain as "QNotch/Notify" and read only when first needed; requests with an Origin header or a non-loopback Host are refused; 64 KB limit). Titles, bodies and labels are capped and sanitized; action links are limited to http, https, vscode, vscode-insiders, cursor and claude; `focusPid` resolves to the nearest app above that process and brings it forward. A toast shows as a peek beside the notch (one per app per second; waiting notifications stay until answered), the right wing shows the unread count, an error can open the panel, and **Quiet during calls** silences toasts while the microphone is in use. History (`notifications.history.json`, 1–30 days, at most 500) keeps link buttons only; notifications still waiting at quit show as Expired. Senders can be muted per app. macOS offers no public API to read other apps' notifications, and this feature does not try.
- Agents shows live Claude Code and Codex sessions. **Connect** in Settings, Agents adds QNotch's hooks to `~/.claude/settings.json` (and `~/.claude-*` folders, or `CLAUDE_CONFIG_DIR`) or `~/.codex/hooks.json`: async command hooks that run `QNotch agent` (Codex: `QNotch agent codex`). Key order, comments-free content and the user's own hooks are preserved, a `.qnotch-backup` is made before the first change, writes are atomic, and Disconnect removes exactly QNotch's entries; another QNotch copy's hooks are detected ("Use This Copy"). Each event sends one line over `agents.sock` (mode 0600) in the data folder; the hook always exits 0 and exits at once when QNotch is not running. Sessions move between Ready, Working, Needs you and Done with the Windows rules (out-of-order guard, waits keyed to the tool asked about, no row revived after SessionEnd). The right wing shows "api needs you" or "2 working"; a peek and an optional sound (not during calls) announce "Needs you" and finished turns. A process-exit source drops sessions whose terminal closed. **Show** brings the terminal or app forward and opens the Claude or Codex app link when the hook found one. Today's tokens and their cost at API list prices (Settings, Agents, **Show API cost**, on by default; off shows tokens only) are read incrementally from Claude Code transcripts (and their subagent files) 3 seconds after an event, with the Windows price table. Titles come from T3 Code, then Codex's `session_index.jsonl`, then the transcript. While T3 Code runs, its sessions are read from `~/.t3/userdata/statev2.sqlite`, opened read-only with the system SQLite; an FSEvents stream on that folder (1-second latency) triggers reads only when the database or its WAL is written, and T3 rows merge with hook rows by native session id. Open brings T3 forward and opens `t3code://threads/…`. Under each session, the processes its shell tools started (dev servers, watchers) are listed with memory, CPU and listening ports, and processes whose shell or agent ended show under "Left running"; **Stop** (confirmed) sends SIGTERM, then SIGKILL after two seconds, only to processes whose start time still matches. The process tree is read with libproc every 2 seconds while the Agents tab is on screen, every second for 10 seconds after a shell tool starts, and when a tool ends or an agent exits; never while collapsed and idle.
- Weather shows the MET Norway forecast for a place picked with the yr.no search in Settings, Weather (no location services): a two-column Home card with now and four days (days follow the place's time zone; each day's symbol is the six-hour period nearest noon), and the temperature beside the notch (optional). Requests go to api.met.no (only the place's coordinates) and www.yr.no (the search text), with a QNotch User-Agent. Refreshes are one-shot timers at MET's Expires plus 30 seconds (10 minutes to 2 hours) with If-Modified-Since; failures retry after 10 minutes, rate limits after an hour; the forecast is cached atomically in `weather-cache.json` and shown as saved while offline. MET symbol codes are drawn with the yr.no weather symbols (github.com/metno/weathericons, MIT), the same PNGs Windows ships; the build copies them into `Contents/Resources/WeatherIcons`, and multicolor SF Symbols stand in when a file is missing. Data: MET Norway, CC BY 4.0.
- GitHub shows your contribution graph (53 weeks × 7 days, drawn in one pass only when the data changes) with totals, streak and a legend on a two-column Home card. **Sign in with GitHub** (Settings, GitHub, above the token box, and the welcome tour) uses the OAuth device flow: it shows a code, **Copy code and open GitHub** copies it and opens GitHub's page in the browser, and QNotch polls at GitHub's interval (5 seconds more after `slow_down`) only while that view is on screen; Cancel, leaving the page, closing the window or the code expiring stops it, and an expired code, a denial on GitHub or a network error offers **Try again**. Only `read:user` is requested. The OAuth App's public client ID is `GithubOAuth.clientId` in `Modules/Github/GithubSignIn.swift` (no client secret; its tokens do not expire, so there is no refresh); without one, the sign-in buttons are hidden and only the token box shows. Or add a personal access token (classic, read:user; repo for private activity). Either token is stored in the Keychain as "QNotch/GitHub" and sent only to api.github.com; the token, device code and user code are never logged. The GraphQL calendar refreshes with one-shot timers every hour (10 minutes after a failure); the last graph is cached atomically in `github-cache.json` and shown as saved while offline. Remove Token deletes the Keychain item and the cache.
- AI apps and usage: a Home card and an AI tab show plan usage for Claude Code (5-hour and weekly windows, plan, banked resets) and Codex, laid out as on Windows: on Home each provider's first window as a bar with the second window and the reset below; in the tab a card per provider (two to a row) with every window's bar, used and left, the reset, the plan chip and banked resets. Unavailable readings say why and never show a number. Every Claude Code account is read on each refresh: `~/.claude` (or `CLAUDE_CONFIG_DIR`) and every signed-in `~/.claude-*` folder. They share one row, and with two or more its account picker ("Claude: work") switches the reading shown without a new request; Settings, AI names each account. Claude usage comes from Claude Code's own command line tool, as in T3 Code: on each refresh QNotch starts `claude` once per account (CLAUDE_CONFIG_DIR set for other folders) in stream-JSON mode with no settings files, hooks, MCP servers or saved session, sends only the `initialize` and `get_usage` control requests (no prompt, so no model request), reads the answer, and stops it after at most 20 seconds. The CLI reads its own sign-in. Banked resets are not in its answer, so for them QNotch reads the login the way Claude Code stores it, with `/usr/bin/security find-generic-password` ("Claude Code-credentials", or with the first 8 hex digits of the config folder path's SHA-256 for other folders; that tool is already on the item's access list, so macOS shows no prompt), falls back to `.credentials.json`, and sends the token only to api.anthropic.com's usage endpoint; any failure there just hides the banked count. An account counts as signed in when its `.claude.json` has an account record; the plan tier comes from there too. Codex usage comes from the newest `~/.codex/sessions` rollouts (no network) and banked resets from a short `codex app-server` call. Refreshes are one-shot timers every 5–60 minutes (default 10). Known AI apps (ChatGPT, Claude, Codex, Cursor, Antigravity) and any app you add fill six slots opened with ⌃⌥1…⌃⌥6 (Option-digit types characters on macOS); a slot's hotkey is registered only while it holds an app. Search opens apps by name.
- Edit mode: the pencil in the header (on Home) makes cards and module tabs jiggle (only while editing and only with motion on); drag a card to another place, or a tab sideways. A press on a tab without a drag still opens it, and card content is inert while editing. The order is saved as `cardOrder` and `tabOrder` in `general.json`; cards and tabs of features that are off keep their place for when they come back. The panel never auto-closes while editing; leaving Home or closing the panel ends it.
- Game mode: while a game is in front of the notch's display, the notch steps aside. The panel does not open (hover, clicks, hotkeys, file drags, peeks and automatic opening are off), the surface ignores the pointer, and the wings show only the features chosen in Settings, Game mode, at the chosen opacity. Detection is event driven: app activation, Space and display changes trigger one `CGWindowListCopyWindowInfo` check of the frontmost app's window bounds (no Screen Recording permission is needed for owner and bounds); entering waits 250 ms, leaving is immediate. By default only apps whose `LSApplicationCategoryType` is a games category count, so full-screen work apps keep the notch; **Any full-screen app** restores the Windows rule. Always and Never lists take bundle ids (Never wins). ⌃⌥G and the menu-bar item set Automatic, On or Off for the session. macOS reports no event when another app resizes its own window, so a game that goes borderless full screen without changing Space is noticed at its next activation.
- Scheduled tasks lists your launch agents in `~/Library/LaunchAgents` (the macOS counterpart of Windows Task Scheduler tasks): the schedule from `StartInterval`, `StartCalendarInterval`, `KeepAlive`, `WatchPaths` or `RunAtLoad`, the next calendar run, whether it is running, paused or failed (last exit status), and the command. Agents whose program lives in an app bundle or Application Support are hidden unless you show them. **Pause** runs `launchctl disable` and `bootout` (it stays off after a restart); **Resume** runs `enable` and `bootstrap`; **Delete** unloads it and moves the plist to the Trash after a confirmation. The list is read when the panel opens (one `launchctl list` and one `print-disabled`, off the main thread); nothing runs while collapsed. System daemons and agents in `/Library` are not touched.
- Now playing covers Music and Spotify, the players macOS lets other apps follow publicly (reading any app's media session needs the private MediaRemote framework, which QNotch does not use). Their distributed notifications (`com.apple.Music.playerInfo`, `com.spotify.client.PlaybackStateChanged`) report the track and play state without any permission. Apple Events, which macOS asks about once per player (Privacy & Security, Automation), are used for play/pause, next, previous, seeking, the current position when the panel first opens, and Music's artwork; a player that is not running is never launched. A two-column Home card, a Media tab (both show a centered "Nothing playing" placeholder, as on Windows, while neither player has a track), and the title beside the notch while playing; the position is interpolated once a second only while it is on screen. Spotify only offers its artwork as a web address, which QNotch does not fetch; its app icon is shown instead.
- Updates (Sparkle 2): Settings, About has **Check Now**, **Check automatically** (once a day), **Install automatically** (download in the background, install when QNotch quits) and **Beta versions**; the menu-bar item and app menu have **Check for Updates…**. The welcome tour's **Check for updates automatically** (on unless turned off; a skipped first-run tour also turns it on) sets Sparkle's `automaticallyChecksForUpdates`, which stores `SUEnableAutomaticChecks` in the app's defaults and so records the choice: Sparkle does not ask again on the second launch. Only an install that never recorded a choice (one from before the tour) still gets Sparkle's question on a later launch. The feed is `UpdateChannel.feedURL`, a signed appcast on the repository's `macos-appcast` branch, never GitHub's global latest release. Sparkle refuses a feed or update without a valid EdDSA signature from `SUPublicEDKey`, verifies the update before extracting it, and installs only a copy signed by the same Developer ID team, then relaunches. Only a Developer ID signed copy constructs the updater: development builds, `--smoke-test`, `--measure` and `QNOTCH_MAC_DATA_DIR`/`--data-dir` runs make no update requests and show "Updates unavailable". Sparkle keeps its own preferences (last check, automatic checks and installs) in the `dev.qnotch.mac` user defaults; **Beta versions** is `betaUpdates` in `general.json` and is not part of setup codes.
- Settings, General, **Share your setup** copies a `qnotch-setup-1:` code (base64url of raw-deflated JSON, the Windows format) with hover and close delays, motion, accent, features, card and tab order, card visibility, game mode basics and the shared fields of Timer, Weather, Notifications, AI and Agents. It uses the Windows field names, so codes work between QNotch for Mac and Windows; Mac-only choices travel in a section Windows ignores. Codes carry no accounts, tokens, history, display, profile or hotkeys (shortcut syntax and keyboards differ). **Check** validates the code (size, depth, string and value limits as on Windows) and lists what changes; **Apply and Restart** writes the settings and relaunches QNotch.
- On a display without a notch, drag the floating pill sideways: it settles at the center or flush with an edge when released within 56 points of one, a double-click re-centers it, and the spot is remembered per display (`pillOffsets`). Windows also remembers a spot per foreground app; the Mac does not.
- When a wing is full, a segment that does not fit moves to the outer end of the other wing if that has room (both wings are as wide as the fuller one); only then are whole segments dropped, farthest from the camera first, rather than truncating them or spilling over the bezel and menu bar.
- Turning a feature off or on in Settings, Features constructs or stops only that module; the others keep running (a countdown survives turning Note off).
- Turning Countdown off takes effect immediately, stops its scheduler, and removes all five contributions. The panel explains how to enable it instead of showing a fake timer.
- Reduced motion follows both the user's local setting and the OS setting and turns every animation off. All animations are finite Core Animation transactions. No display link, frame loop, repeating idle timer, or hidden countdown animation runs.
- Not available on the Mac: media sessions of apps other than Music and Spotify (no public API), GPU temperature, per-app camera attribution, the Windows phone-share server (AirDrop through Share covers Apple devices). A notch that wraps the camera housing never moves. See the [parity table](parity.md) for each feature's status.

## Module and platform boundaries

`Sources/QNotchMac/Shell/` owns AppKit windows, focus, hover, display events, navigation, search hosting, and general settings. `Modules/Contracts.swift` defines five local registries: **cards, tabs, status segments, search sources, and settings sections**. `ModuleList.swift` is the only composition file naming concrete modules. A disabled module is never constructed. Each module owns its state, providers, views, and preferences; it receives visibility and active-tab changes rather than inspecting window internals.

`Modules/Timer/` supplies the real countdown module. A visible running countdown refreshes at most once per second; collapsed or hidden content schedules only its completion deadline. A stopped or paused timer has no scheduled work. Its collapsed segments (a progress ring and the time left) show whole minutes, so a running collapsed timer wakes once per minute and once per second only during its final minute, as on Windows. Completion is a justified one-shot background wake. Sleep/wake and clock-change events reconcile the wall-clock deadline; changing the system clock can change the remaining duration.

`QNotchMacCore` contains Mac-local, testable geometry, countdown, shell-state, settings, and update-channel rules. It is not a cross-platform runtime and is not referenced by Windows. macOS APIs and future credential-store integrations stay inside this implementation.

## Data, permissions, and diagnostics

Default local root: `~/Library/Application Support/QNotch.Mac/`. `general.json` stores the selected display, reduced motion, hover and close delays, the pin, accent, display name, hidden cards, the turned-off modules (`disabledModules`; the first milestone's `timerEnabled` is migrated) and `onboardingDone` (the welcome tour ended; local, never in setup codes); `timer.json` stores duration and completion sound; `note.txt` holds the note; `profile.png` the profile picture; `filetray.json` the tray's bookmarks; `clipboard.json` the opt-in text history; `weather.json` and `weather-cache.json` the place, units and forecast; `notifications.json` and `notifications.history.json` the notification settings and history (`notify.sock` is the live socket); `colorpicker.json` the recent colors; `gamemode.json` stores game mode preferences; `hotkeys.json` stores changed shortcuts (id to gesture, empty for off); `sounds.json` stores chosen sounds (id to system sound name or file path). Writes are atomic. Missing files use defaults. Corrupt files remain intact until the user explicitly saves replacement preferences; Settings reports unavailable storage and session-only changes. Display IDs are supplied by macOS and may change after hardware/system reconfiguration; fallback is explicit.

`logs/session.log` contains bounded startup timing only and is replaced each launch. It contains no account identity, display names, credentials, or user data. `QNOTCH_MAC_DATA_DIR` and `--data-dir` replace the entire root, including logs and the instance lock. Secrets must go in Keychain when a module eventually needs them. Network requests: Weather (api.met.no, www.yr.no) GitHub (api.github.com, only with your token; github.com/login/device/code and github.com/login/oauth/access_token only after you click **Sign in with GitHub**, and only while its code is on screen), AI usage (api.anthropic.com, with Claude Code's own sign-in) and updates (the appcast on raw.githubusercontent.com and the update itself from github.com; signed release builds only, with Sparkle's standard User-Agent and no system profile). The welcome tour itself makes no requests; its place search is the Weather search, and its GitHub row is Sign in with GitHub. There are no analytics, Accessibility or Screen Recording permissions, or notification authorization prompts. Notifications listens on a per-user socket and on 127.0.0.1 only; secrets (the notification token) live in the Keychain. Diagnostic runs (`--smoke-test`, `--measure`) keep secrets in memory and never touch the Keychain.

Debug channel ([spec](../../spec/diagnostics.md#debug-channel)): off unless the app is started with `--debug-control`, which opens `debug.sock` in the data root (mode 0600, only the same user's connections accepted, a stale socket from a killed run replaced but a live one or any other file left alone, removed on quit); no setting, `--smoke-test`, `--measure` or `--snapshot` opens it by itself, and a `--debug-control` run does not show the welcome tour by itself. `QNotch.app/Contents/MacOS/QNotch debug <cmd> [--<arg> <value>…]` sends one JSON-line request (`ping`, `state`, `open`, `close`, `select-tab`, `settings`, `onboarding`, `outline`, `snapshot`, `press`, `type`, `key`, `hotkey`, `game-mode`, `quit`; run `--help`) to the instance found through `--data-dir`, `QNOTCH_MAC_DATA_DIR` or the default root and prints the result as JSON (exit codes 0 ok, 1 failed, 3 no instance with the channel open, 4 bad usage). Socket I/O runs on a background queue, each command on the main thread, one at a time per connection; a command answers once the UI has settled: two checks 1/60 s apart find layout done, the notch not morphing, no window mid-fade and no finite Core Animation animation in any visible window (endless loops such as the edit-mode jiggle do not count), or after 3 seconds. Controls are found by identifier in the visible windows and driven as input would be (`performClick`, a switch's own action, the field editor's `insertText`, key events through `NSApp.sendEvent`); `hotkey` runs the Carbon shortcut's own action. `state` frames are points with the origin at the top left of the primary display. `snapshot --window settings` renders the current page, like the smoke test's `settings-<id>.png`. The channel can read whatever QNotch shows and press any control, which is why it stays off by default. `Shell/DebugChannel.swift` (`DebugChannel.start(shell:directory:)`), `Shell/DebugCommands.swift`, `Shell/DebugClient.swift` and `QNotchMacCore/DebugProtocol.swift`.

`smoke.sh` uses a unique temporary data root, exercises the actual AppKit shell and timer scheduler, exports the pill in its states (idle, running, capture, peek, waiting, agent, game mode), Home (also in edit mode), one PNG per Home card, per tab and per Settings page, drives the real `notify` and `agent` command-line verbs and loopback HTTP, a card drag, game mode, pin, accent and module switching, checks that the welcome tour did not open by itself, then opens it as Settings, About does and steps through every step (`onboarding-<step>.png`, `onboarding-open-tried.png` and `onboarding.txt`: the toggle gesture is noticed in the tour window without opening the panel, Return continues, a feature switch stops and restarts its module, the Connect step has the GitHub and Weather rows, **Open QNotch** opens Home with the keyboard and records `onboardingDone`, Esc skips a reopened tour; it never touches Sparkle settings or login items), uses a private pasteboard and demo data with no network requests or Keychain access, and requires a final `done` in `dist/macos/smoke/smoke.txt`. It fails without a graphical display or on a timeout. Inspect the PNGs after UI changes; snapshots do not capture another application's screen. CI uploads them as `macos-smoke`. The smoke test checks the actual AppKit window frame and view bounds against the bezel, camera exclusion, and side wings. Geometry tests cover bezel attachment, camera-safe placement, non-notched external displays with negative origins, and clamping; physically reconnecting multiple displays still needs a manual hardware check.

## Performance: targets and evidence

See the [recorded Mac measurements](performance.md) for the dated build, hardware, results, and limitations.

Mac development targets: collapsed stopped-timer CPU at or below 0.1% of one core, zero app draw callbacks after settling, no app-scheduled repeating idle work, process-start-to-panel-ordering below 500 ms, and resident memory below 80 MiB. These are targets, not guarantees or imported Windows benchmarks. A collapsed running timer wakes once per minute (once per second in its final minute); an expanded running timer can wake once per second.

Run the release build, keep the pointer away from the pill, and measure an isolated process:

```sh
bash scripts/macos/measure.sh
```

This waits three seconds, then records one 30-second collapsed-idle interval using `proc_pid_rusage` CPU time, resident size, and interrupt wakeups, plus app view draw counters. The two interval endpoints add no sampling loop. `dist/macos/measure/performance.json` records the source revision/dirty flag, app version, hardware model, physical memory, OS, state, method, elapsed interval, process-start-to-panel-ordering, and measurements. The launch metric uses the kernel process start timestamp and `mach_absolute_time`, and ends just after the panel is ordered front. It includes process startup and app initialization, but excludes waiting in Launch Services and first compositor presentation; it is not a click-to-visible benchmark. Draw callbacks do not establish compositor/GPU repaint counts, and interrupt wakeups are not total thread wakeups. Use Instruments/Energy Log for those measurements before making stronger claims. Include commit/build, hardware, memory, OS, state, interval, and method in any recorded evidence; keep results separate from targets.

## CI and future releases

The `macos` CI job uses an Apple silicon `macos-14` runner to build the real target, run XCTest regressions, and run native UI smoke validation. It is part of the required `build` aggregate alongside Windows, repository, and website validation; any failure, cancellation, or skipped dependency rejects the gate. PR builds do not use signing secrets and publish nothing.

The Mac update channel is `QNotchMacCore/UpdateChannel.swift`: the Sparkle appcast of `macos-vX.Y.Z` releases on the `macos-appcast` branch, never GitHub's global `/releases/latest`. See [Mac updates](../releases.md#mac-updates-sparkle) for how releases reach it.

Mac releases are signed with Developer ID under the hardened runtime, notarized, stapled, and published as `QNotch-macos-arm64.dmg` by the `macos-v*` tag workflow; see [Releases](../releases.md#mac-channel) for the workflow, its credentials, and a local signed build. Windows tags, updater endpoint, filenames, ZIP layout, and publish profiles remain unchanged.

Before the first public download, verify installation of the published disk image on a clean Mac and on macOS 13.
